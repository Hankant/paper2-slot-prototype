## 2. 必须修复的问题

### R1 / P1：事件接口丢失实际作答内容

位置：`src/contracts/envelopes.ts:23`、`src/contracts/interfaces.ts:36`、`src/contracts/validators.ts:108`。

规格要求的 `payload` 没有进入 `EventEnvelopeBase`、保存方法参数或 `eventEnvelopeSchema`。实际把 `{ payload: { machine_id: 'B', display_position: 'center' } }` 加到合法事件后调用 parse，返回对象的 payload 为 undefined。校验没有报错，却移除了作答。

同一 schema 接受没有 payload、没有 trial_id 的 prediction 事件，也接受 confidence=150 的事件（其 payload 随后被丢弃）。若 C 按指南“先校验再保存”，就只会保存事件标题和时间，无法恢复预测、信心或来源选择。目前尚无真实记录受损，这是接入前已复现的数据通路缺陷。

修复要求：A 定义按 event_type 区分的事件联合类型和 payload 校验，规定每种事件所需试次/阶段/单位；ResultStore 接受完整事件。验证“parse 后内容保留”及负例，不仅验证 success=true。选择符合计划的字段名后同步 fixture 和消费者。

### R2 / P1：公共服务没有传递建议内容的渠道

位置：`src/contracts/trial-types.ts:21`、`src/contracts/trial-types.ts:49`、`src/contracts/interfaces.ts:27`。

PublicTrial 只有 advice_timing，没有建议机器、来源、建议编号或可见状态；TrialService 也没有其他取建议接口。反馈仅有几个布尔结果，没有规格要求的最终预测。ParticipantPrediction 类型已定义但没有接到事件或服务入口；对应 TrialFeedback 运行时校验也不存在，交接中的“所有公共数据类型均有 schema”不成立。

B 无法单靠冻结接口呈现来源建议，D/C 无法沿同一契约传出材料，只能各自扩字段。不能因此认定接口已具备并行实施条件。

修复要求：A 定义阶段可见的建议数据及其读取路径、来源选择/最终预测记录和反馈校验。精确定义 after_choice 指的是独立预测后还是来源选择后；支持演示选择即可，不替用户锁定正式 T03。补一条“当前题→独立预测→来源选择/建议揭示→最终预测→反馈”的契约样例，证明双方无须私加字段。

### R3 / P2：保存回执接受自相矛盾的数据

位置：`src/contracts/validators.ts:131`、`src/contracts/persistence-types.ts:29`。

实测下列输入都被接受：remote 回执中的 persisted_at 和 receipt_id 同时为 null；同一个 event_id 同时出现在 acknowledged 与 rejected 中。字段各自合法不等于保存结果合法，这会让队列无法确定应删除还是重试该事件。

修复要求：校验 remote 所需确认信息、非 remote 字段语义、三个事件集合互斥和内部唯一；适配器另对照请求检查回执 ID 属于本次提交，并把遗漏项保留为未确认。schema 通过也不能替代实际远程持久化证据。

### R4 / P2：所谓生产能力检查允许没有持久化存储的后端

位置：`src/contracts/capabilities.ts:31`、`config/demo.ts:144`。

satisfiesRequired 只要求 idempotentWrites、serverControlledTrials。实测 persistentResults=unsupported、serverScoring=unsupported、resumeSession=unsupported 时仍可返回 true，只要前两项为 supported。该函数被 demoCapabilitiesSatisfyProduction 包装并在交接中称为生产门槛，语义过强。

修复要求：将必需能力与实际运行模式绑定。正式收集至少不能在持久保存不支持时通过；其余能力依具体正式协议明确判定。LocalDemo 显式走演示路径。尚无实现的 individualEntryCodes 不应在 demo.json 中声称 supported。当前 demo 的整体检查确实返回 false；本发现针对可被其他适配器触发的错误准入。

### R5 / P2：演示配置靠类型断言，缺少运行时验证

位置：`config/demo.ts:54`、`config/demo.ts:123`、`config/demo.ts:128`。

loader 只检查 config_version 和 simulation，其余使用 `as DemoConfigRaw`。独立测试用 mock JSON 替换输入、未改真实配置，发现 main=-12 仍能加载；no_real_personal_data=false 仍能加载，输出还被固定改写成 noRealPersonalData=true。负值和错误标识会被带入或掩盖。

修复要求：在字段转换前以 schema 完整验证原始配置，拒绝负题量、无效枚举、版本冲突及矛盾模拟标识；不要把输入中的错误标识静默改成 true。保持 TypeScript 类型与实际校验结果一致。

### R6 / P2：机器编号/位置可重复，后续无法唯一映射

位置：`src/contracts/validators.ts:46`。

把同一机器记录重复三次（机器 ID 与位置都相同），PublicTrial 校验仍通过。根据已约定的逻辑 ID 与显示位置分离要求，这样的材料无法可靠绑定点击与答案。

修复要求：校验机器 ID 和显示位置唯一，并在材料审计中核对数量与 demo 配置匹配、历史/建议引用有效。不要把演示的三机器要求擅自升为正式研究条件。

### R7 / P2：交接入口和冻结文档不一致

位置：`handoffs/A/2026-09-17T22-11+08-00_g0-handoff.md:34`、`src/contracts/index.ts:4`、`docs/CONTRACTS.md:3`。

交接要求 `from 'src/contracts/index.js'`，barrel 注释建议 `@contracts`，但 tsconfig/Vite 都未配置对应 alias。用当前 TypeScript resolver 从 `src/experiment/review-consumer.ts` 检查，两者均 unresolved；`../contracts/index.js` 可正确解析。交接还列出了实际未导出的 EventEnvelope 名称。

CONTRACTS 仍为 DRAFT，而 STATUS 宣称已冻结 0.1.0/DONE；交接让 C 改 bootstrap，原路径职责表仍由 A 独占。新 agent 照其中任一份实施都会遇到不一致。

修复要求：选择一种真实可用的导入方式，做一个消费者编译样例；同步接口文档、导出名称、版本、路径所有权与检查点。A 应把当前状态改为待修正/待复审，修正并验证后再释放 G1。Q 本轮不覆盖 A 的看板或历史报告。
