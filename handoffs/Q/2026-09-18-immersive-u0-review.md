## 需要先纠正的接口与交接问题

### R1：完成状态转换互相矛盾

位置：`docs/CHAT_STATE_TABLE.md:14–15,30`。

第一张表规定 `streaming` 收到 `completed` 后进入 `awaiting_completion`，该状态又等待 `completed`；第二张表规定同一次事件直接进入 `completed`。供应商通常只发一次终结事件，按第一张表实现可能一直无法完成。建议统一为“接收完成 → 校验/绘制完成 → completed”，将尚未收到终结事件和尚未完成绘制明确区分，只保留一份权威转移规则。

### R2：迁移说明仍引用已删除的写入接口

位置：`src/contracts/chat-service.ts:13`；A 的 `2026-09-18_imm-u0-stream-interfaces.md` 迁移说明。

新说明要求先调用 `recordSourceChoice(...)`，但当前 `TrialService` 已无此方法。正确路径是通过 `ResultStore.saveEvents` 保存 `source_selected` 并处理确认，再读取授权建议。应按当前接口修正，不能让 B/C 按旧说明重新实现另一条写入路径。

### R3：重试规则会改变同一次建议

位置：`docs/CHAT_STATE_TABLE.md:56`；对照 `docs/IMMERSIVE_UI_PLAN.md` 4.3。

状态表强制重试使用新 request ID，并禁止复用；方案则要求恢复同一回答、复用请求 ID。新 ID 在真实模型模式下可能导致重新生成和不同建议。应区分恢复/传输重试与用户明确发起的新生成，定义同一逻辑请求、尝试次数和已呈现前缀的关系。

### R4：聊天完成、参与者提交和保存确认被混用

位置：`docs/CHAT_STATE_TABLE.md:30,61`；`src/contracts/chat-service.ts:19–20`。

表中把流结束写为触发 `final_prediction_submitted`，应改为只开放参与者确认入口；只有参与者实际确认才生成最终预测事件。聊天内容、呈现进度仍需独立保存，最终预测不能代替聊天记录。

表中还要求把模型错误码写入 `SaveReceipt.rejected_events`，但该字段是保存被拒的事件 ID 列表；模型出错和数据保存失败不是同一件事。取消一次回答也不能自动把整个实验会话改成不存在于当前契约的 `session_status='cancelled'`。这些状态要进入明确的聊天事件，并保持原有保存回执语义。

### R5：新增测试没有验证完整流的不变量

位置：`tests/contracts/chat-events.spec.ts:60–64,90–95`；`src/contracts/validators.ts:625–630`。

当前逐条解析 fixture 的字段；“序号单调递增”测试仅断言两个固定样例是 0 和 1，再拒绝负数。没有状态验证器或适配器测试来拒绝乱序、重复 started、缺失/重复终结、跨请求混入；hash 也只校验格式，未重算文本摘要。

这批测试可证明字段校验可用，不能作为流式实现、取消/恢复、幂等和内容完整性通过的证据。下一轮应使用可执行流消费者/适配器，输入独立异常序列再验收。
